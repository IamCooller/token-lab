Qwen3.6-35B-A3B has 16.1 GB of experts, more than a 16 GB laptop can hold next to everything else. The engine keeps the rest of the model in memory, reads the experts the router picks from the SSD, and keeps a small cache of experts for every layer. Reading every chosen expert from the SSD would give about 5 tok/s (an estimate). A 1.32 GB cache brings that to 17-20 tok/s, the default cache to about 25 tok/s when RAM is free, and a 6 GB cache with run-ahead and the draft head to 54.6 tok/s on code. This page explains why it is slow, what made it faster, and every idea tried so far, the failed ones included.

Every number is marked: measured · machine is a run, estimate is a model or an approximation, illustration is not data. Device colours are the same throughout: SSD CPU GPU. Unfamiliar words are explained under Terms.

Why this is hard

A token passes through all 40 layers of the model, and in each one the router picks 8 of 256 experts. One token needs 320 experts, about 503 MB of expert weights, and the next token picks a different set. All 10,240 experts take 16.1 GB, which does not fit next to the 1.1 GB rest of the model, macOS and the apps, so they stay on the SSD, which reads 3.4-3.6 GB/s. Reading every chosen expert would cost about 158 ms per token, and the whole token about 195 ms, or 5 tok/s (Figure 1).

Two things cut the reads. A cache of 21 experts per layer, the arena, takes 1.32 GB, and the router is nudged toward experts already in it, the cache bias. Together they bring the reads down to a median of 76.7 MB per token, and 43.5% of those bytes come from the macOS file cache instead of the SSD.

After that the SSD is no longer the main cost. At 21 slots the reads take 19.2 of a token's 56.5 ms (Figure 3). Most of the rest, 28.9 ms, is the CPU waiting for the GPU at 40 synchronizations per token, one per layer: the CPU has to read each layer's router choice back from the GPU before it can fetch that layer's missing experts. Reading the next layer's experts during the current one looks like the fix, and the next layer's choice can be guessed well, 80% of its 8 experts. In a paired run it did not help: 0.999×, with 112k rows of guessed expert weights read to save 25k blocking ones. The guessed reads share the one SSD with the reads that block; why the saved waits did not show up at all was not established.

The ceiling is the GPU. One forward pass touches 1730 MB in memory, 1604 MB of weights and 126 MB of recurrent state, and moving that takes 16.5-18.4 ms at the measured bandwidth. At one token per pass that caps decode at 54-61 tok/s. With the draft head one pass checks two positions, so the cap holds per pass, not per token.

Deep dives

One decoded token, taken apart: 21 slots per layer, cache bias 0.5, the Python path, no draft head. The model has 40 layers, 30 GatedDeltaNet and 10 with full attention (every fourth: 3, 7, … 39). Each layer's router picks 8 of 256 experts, and one shared expert stays resident. An expert that is not in the arena is read from the SSD or copied from the macOS file cache. Nothing overlaps, so a token's time is a plain sum over layers \ell of CPU graph build h_\ell, GPU wait g_\ell and expert reads r_\ell:

\begin{aligned} t_{\text{token}} &= \sum_{\ell=1}^{40}\bigl(h_\ell + g_\ell + r_\ell\bigr) \\ &\approx 8.3 + 28.9 + \sum_{\ell=1}^{40} r_\ell \ \text{ms} \end{aligned}

Of the 50-56 ms, the GPU does about 22 ms of real work estimate. Reads, CPU↔GPU round trips and graph building take the rest, and all three come from the same place: about half of the layers miss the arena on every token.

How this page's cost model is computed
  1. The Python line is measured: an arena sweep on the M4 (the 35B server setting with an arena of N slots) at 21, 29, 37, 48, 56 and 64 slots, joined by straight lines. The 96-slot point (33.45 ms on code, 32.78 on prose) comes from an earlier run on an older engine version, which is why the 64 → 96 segment is dashed.
  2. Everything that is not a read is held constant. The instrumented 28.9 ms of GPU wait plus 8.3 ms of CPU, less the ~14% timer overhead, gives C = 32.6 ms. Inside it, GPU work is about G = 22.0 ms (estimated from bytes and a per-layer constant), the CPU graph build H = 7.3 ms, and the remaining 3.3 ms are synchronization round trips. The reads are what is left, and the read waves per token, W, are counters from the same sweep: R = T_{\text{meas}} - C
  3. Stage 2 keeps one token in flight, and the CPU builds the graph ahead while the GPU runs. A read wave then costs 0.074 ms instead of 0.29, and the GPU↔CPU handshake adds 3.5 µs plus 17 µs of GPU slow-down per layer (stage 1 measurements). This is the optimistic edge, with everything removable removed: t_2 = 22.0 + 0.8 + \bigl(R - 0.216\,W\bigr)
  4. Draft head. A two-position pass costs c_2 times a one-position pass, and a share a of drafts is accepted (0.98 on code, 0.66 on prose, so 1.98 and 1.66 tokens per round). c_2 = 1.94 at 21 slots, which puts the draft head on code at ≈1.02×, inside the measured 0.98-1.13× (0.98× on a long code review, 1.03-1.13× on tool calls), and 1.62 at 96 (22.38 → 18.30 ms), linear in between. On prose at 21 slots this model says the draft head slows decoding down; that is an estimate, not a measurement. t = \frac{c_2\, t_{\text{pass}}}{1 + a}
  5. Stage 3 runs the token and its draft as two chains, the draft one layer behind, on one GPU and one SSD; whichever step is ready first goes next. The draft reads 0.9 of the main token's reads (1.9× together, offline replay), and the draft head costs 3.3 ms per round estimate. The round is divided by 1 + a. When a plain two-position pass comes out faster, the model uses that instead.
  6. Ideal overlap runs the three lanes at the same time: t_{\text{ideal}} = \max\bigl(t_{\text{GPU}},\ t_{\text{SSD}},\ t_{\text{CPU}}\bigr)
  7. With cache bias 0 the router ignores the arena. Replaying the router trace gives ~2.14 times the misses (128.7 against 60.0 per token), so R \to 2.14\,R; the number of read waves is left as it is. The factor was measured at 21 slots and is applied at every size, so this is an estimate.
  8. The bands are earlier estimates, made before the measurements, not this model. Stage 2 was expected at 1.15-1.27× (conservative) up to ~1.39× (design simulation) over the Python path, and stage 3 on code at another ×1.25-1.35. They were stated for 21 slots; other sizes reuse the same factors.

The literature points the same way. Spiking LLMs pay off on neuromorphic chips such as Intel's Loihi 2 (Abreu et al., 2025), or in long attention, but not on a Mac. On a GPU the sparsity that works is activation sparsity (TEAL), and on the experts of the 35B model it gives about 1.1×, so it was not built.

A brain keeps its synapses where it computes. The nearest thing on a Mac is the arena: the expert is already in memory and nothing crosses the bus from the SSD. Of the exact levers measured so far, it is the strongest.

Engine

I keep the dense part of the model in memory: attention, routers, embeddings and the shared expert. The routed experts, 16.1 GB for the 35B, stay in one packed file on the SSD. Each layer gets an arena, a small LRU cache of expert slots. By default the arena is elastic, 21 to 60 slots as free memory allows; unless a number says otherwise it was measured at 21 slots, 1.32 GB across all 40 layers. When the router names its 8 experts, hits are used where they sit. A miss takes the least recently used slot and is read straight into it by a pool of reader threads. The router is also biased toward experts that are already resident, within a cap on how much of its weight it may give up, which halves the misses in replay.

Most of the remaining work went into hiding that wait. Run-ahead decoding removes the GPU's idle time between layers and pays off with a big arena (×1.49 at 96 slots), but at 21 slots about 19 of 40 layers roll back and it loses. The C++ helper removes the same synchronization without rollbacks and gives ×1.30 at 21 slots. Prefill goes layer by layer and reads each expert once per pass. The server keeps recent conversations, so a follow-up prefills only what it adds. The same engine runs on Linux with an NVIDIA GPU through MLX's CUDA backend.

The hot path on a miss

Related work

  • LLM in a flash (Alizadeh et al., Apple, ACL 2024) keeps a model's weights in flash memory and loads what each token needs into DRAM, reusing recently loaded neurons and reading larger contiguous chunks.
  • PowerInfer (Song et al., SOSP 2024) keeps the neurons that fire for most inputs on a consumer GPU and computes the rest on the CPU.
  • KTransformers (Chen et al., Tsinghua University and Approaching.AI, SOSP 2025) runs a MoE model's experts on the CPU from system RAM, and attention and the shared experts on the GPU.
  • llama.cpp memory-maps the model file by default and leaves the paging to the operating system; it is the comparison above.
  • Mixture of Cache-Conditional Experts (Skliar et al., Qualcomm AI Research, TMLR 2025) adds a bonus to the router scores of experts already in a phone's DRAM cache, without training. The cache bias here is that idea with two changes: the bonus scales with this token's spread of router probabilities, where the paper uses an average spread of the router logits, and a cap stops a layer from giving up more than 20% of the router's weight.
  • ReMoE (Zhu et al., ICML 2026) fine-tunes the router to reuse recently chosen experts. It needs training for each model, so it was not tried here.

What differs here: whole experts read from an SSD straight into fixed per-layer slots on a 16 GB laptop whose CPU and GPU share memory; the finding that with a small cache the per-layer CPU-GPU synchronizations cost more than the reads; and a log kept on one machine, failed ideas included.

Method

Every number on the page is a measurement, an estimate or an illustration, and says which. A measurement names its machine and setup. Estimates come from a model or a replay and are set in italics with a dashed underline. Speed numbers come from one M4 MacBook Pro with 16 GB, NVIDIA numbers from one Linux PC with an RTX 5060 Ti. Repeat counts differ: the arena sweep and the 96-slot runs are medians of two runs, the C++ helper's gain is the median of nine alternating pairs, conversation reuse is a mean over 100 paired requests, and the 56.5 ms breakdown, the NVIDIA speeds and the hang-up rows are single runs. Decode speeds are medians of the gaps between tokens. This is a project log, not a general benchmark. The page itself loads no model; the layer-by-layer replay in Figure 4 uses a router trace recorded on the same machine.

A speed change counts as lossless when its outputs are greedy-identical to the baseline up to bf16 ties.2 When they are not, it has to pass a paired GSM8K / HumanEval comparison in which an exact McNemar test finds no significant difference. Lossy changes are reported as lossy. Ideas that did not pay off stay in the idea list as dropped, with the number that closed them.

Limitations

  • The quantization's own cost is not reported. The 35B's experts are stored at 4 bits in 20 layers and 2 bits in the other 20. Every "identical" on this page compares against that same quantized model, not against a 4-bit or bf16 one.
  • The cache bias may cost a few points; the test is too small to say. On the 35B, where it is on by default, against exact routing: GSM8K 82 vs 87 of 100 (p 0.18), HumanEval 151 vs 151 of 164 (p 1.0); pooled, the 95% interval for the difference is −4.9 to +0.9 points. In 8 of the 9 GSM8K disagreements the losing answer was cut at the 512-token limit; with 1024 tokens those problems give 94 vs 96 (p 0.5). Teacher-forced on about 4,400 tokens of public benchmark text, the bias changes the top next-token choice at 2.6% of positions, two thirds of them bf16 near-ties. Decoding in the same test was 1.6-1.8× faster with it. On Qwen3.8-Flash-Next, with the same 20% cap: 82 vs 79 (p 0.45), 152 vs 150 (p 0.63).
  • The quality tests are small. 100 GSM8K problems and 164 HumanEval tasks; the McNemar test looks only at the problems where the two versions disagree, for conversation reuse 3 to 0 and 6 to 5, for the cache bias 9 to 4. "Not significant" at this size is weak evidence of no loss; a loss of a few points could pass.
  • One machine. Every Mac number comes from one M4 MacBook Pro with 16 GB and an internal SSD that reads 3.4-3.6 GB/s. A different SSD moves most of these numbers, and many Qwen3.8-Flash-Next results also use a second, external SSD.
  • Few repeats. Most speed numbers are medians of two runs or of a few alternating pairs; the 56.5 ms breakdown, the NVIDIA speeds and the hang-up rows are single runs.
  • The llama.cpp comparison is not equal. Different quantization, llama.cpp on the CPU only because its GPU path ran out of memory, its threads not tuned, a file cache that could not be emptied between runs, and this engine at 21 slots without the draft head.
  • The implementation is not public, so the numbers cannot be reproduced from this page.
  1. Most Qwen3.8-Flash-Next results, among them layer-by-layer prompt reading, the side buffer for guessed experts and conversation reuse, also use an external SSD: first in a USB enclosure (4.7 GB/s together with the internal drive), later in a Thunderbolt one (7.02 GB/s together). ↩

Terms
Mixture-of-Experts (MoE)
A model whose feed-forward part is split into many small networks, the experts. Each token uses only a few of them.
A3B
In a model name, about 3B parameters active per token. Qwen3.6-35B-A3B has 35B in total.
MLX, Metal
MLX is Apple's open-source array framework for machine learning on Apple silicon; the engine is built on it and on the model code of its mlx-lm package. Metal is Apple's GPU interface, through which MLX runs on the GPU.
Expert
One of those small networks. Qwen3.6-35B-A3B has 256 per layer; stored here, one takes 1.2-2.0 MB.
Router
The small layer that picks the experts for a token: 8 of 256 per layer in the 35B.
Dense part
Everything that is not a routed expert: attention, the routers, embeddings and one shared expert that every token uses. About 1.1 GB for the 35B, always in memory.
Arena, slot
The per-layer cache of experts in memory. A slot holds one expert; 21 slots per layer take 1.32 GB over the 40 layers. On Qwen3.8-Flash-Next its size follows a memory budget.
MoE only, dense too
Whether a change helps only Mixture-of-Experts models, or ordinary dense models as well.
Hit, miss
A chosen expert already in the arena is a hit; otherwise it is a miss and has to be read.
File cache
Memory where macOS keeps recently read file data. A miss found there is a copy in memory, not an SSD read.
Read wave
The reads of one layer's misses, issued together.
LRU
Least recently used: when the arena is full, the expert unused for the longest time makes room.
Cache bias
A nudge to the router toward experts already in the arena, 0.5 by default. It changes which experts are chosen, not how much each one counts.
Draft head (MTP head)
The model's multi-token prediction head, a small extra layer shipped with it that guesses the next token. The full model checks the guess in the same pass, so an accepted guess gives two tokens for one pass.
Run-ahead, rollback
The GPU starts the next layer before the CPU has checked the current one for misses. When a miss turns up, the layers computed without that expert are rolled back: recomputed from a snapshot once the expert is read, so the result is exact.
Python path, C++ helper path
The two ways the engine runs a decode step. The Python path goes layer by layer with one CPU-GPU synchronization per layer. The C++ helper path moves the per-layer handoff between CPU, GPU and SSD into a small C++ component. Stage 1 tested the helper without a model, stage 2 put it in the engine, stage 3 added the draft token.
Graph build
The CPU's work of describing a layer's GPU operations; MLX builds a graph of operations and the GPU then runs it.
Prefill, first token
Reading the prompt before the reply starts. Its length is the wait for the first token.
Decode, tok/s
Producing the reply one token after another; tok/s counts decoded tokens per second.
GatedDeltaNet, GDN, ATT
GatedDeltaNet (GDN) is a linear-attention layer with a fixed-size state that is updated every token; 30 of the 35B's 40 layers are of this kind. ATT marks the other 10, with full attention.
Recurrent state
The fixed-size state a GatedDeltaNet layer carries from one token to the next. Reading and writing it moves 126 MB per forward pass of the 35B.
Attention indexer
A small module in Qwen3.8-Flash-Next that picks which blocks of the context an attention layer reads, from a pooled summary of each block (its pooled keys).
Hyper-connections
Qwen3.8-Flash-Next keeps several residual streams and mixes them with small learned matrices.
35B server setting
The server as used day to day for the 35B: the whole prompt read in one pass and up to four conversations kept. The draft head is added where a row says so.
Usual Qwen3.8-Flash-Next setting
The C++ helper on, a memory budget of 6 GB that may grow to 8 GB, and cache bias 0.5 limited to 20% of the router's weight.
Tool-use loop
A conversation in which the model calls a tool, reads the result and goes on, several steps in a row.
RSS, peak footprint
Two memory figures. RSS, the resident set size, counts a process's pages held in RAM. The footprint is what macOS charges the process, GPU buffers included; the peak is its highest value in a run.
IQ4_XS
One of llama.cpp's 4-bit quantization formats.
Copy engine
A unit of an NVIDIA GPU that moves data without using its compute cores.
Greedy-identical
Always taking the most likely token, the changed engine produces exactly the tokens of the baseline.
bf16, fp32
Number formats: bfloat16, 16 bits with fp32's range but fewer digits, and ordinary 32-bit floating point.
bf16 tie
A place where the two best candidate tokens are so close that bf16 rounding can flip the choice (note 2).
GSM8K, HumanEval
Standard test sets: grade-school math word problems (100 used here) and Python programming tasks (164).
McNemar test
A paired test that looks only at the problems where the two versions disagree.
Target
The threshold written down before a run. An idea that misses it is dropped.
Byte floor
The time the GPU needs just to read every byte one forward pass touches in memory, at its measured bandwidth.
Replay
Running a recorded router trace through a simulated cache, without the model.
